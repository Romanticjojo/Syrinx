# 谱面转换调研：PDF / 图片谱 → 带氛围效果的五线谱页面

> 调研日期：2026-08-30 ｜ 面向 Syrinx 演奏应用（曲谱引擎 OSMD + MusicXML，主题 A「暖金 #d9a441 / 晨光青 #5fb8a8 / 玻璃面板」）
> 问题定义：用户手里的谱子是 PDF 或图片（也可能简谱/手写谱），如何变成应用页面里的「标准五线谱渲染 + 光标跟随 + 主题氛围染色」。

---

## 0. 结论速览（TL;DR）

1. **主推管线**：`PDF/图片 → (pdftoppm 转图) → homr 识别 → MusicXML → OSMD 渲染`。homr 是当前开源 OMR 里精度最好、最活跃、命令行最简单的一个（相机/扫描图直接出 MusicXML，单页约 15 秒，CPU 可跑）。
2. **转换放「素材准备阶段」，不放运行时**。Syrinx 是静态 SPA，Song Pack 本就以 MusicXML + 小节时间表为素材形态；OMR 识别应作为**离线/旁路工具链**（脚本或本地小服务）在入库前完成并人工校对，应用内不做 OMR。
3. **没有任何工具能做到「零校对」**。干净印刷谱开源引擎约 70–90% 正确率，手写谱/低清扫描会显著下降。流程必须内置「人工校对」环节（MuseScore 打开 MusicXML 修正）。
4. **许可红线**：homr / Audiveris / Clarity-OMR 都是 AGPL/GPL（传染性）；用它们做**独立转换进程/服务**（不并入前端闭源代码、不随应用分发）即可合规，别把识别引擎塞进前端 bundle。
5. **简谱没有成熟开源 OMR**，推荐「录入」路线：MuseScore 简谱插件（或 domisol 等网页工具）录入 → 导出 MusicXML。自研最小识别器约 20–40 人日，不建议。
6. **PDF 无「语义直转」路径**：从乐谱软件导出的 PDF 只是矢量图形，不携带音符语义；必须重导源文件（mscz/mxl）或走 OMR。

## 2. 推荐管线（含步骤与命令示例）

### 2.1 主推荐：homr 离线转换管线（素材入库阶段）

```
┌────────────┐   pdftoppm -png -r 300    ┌──────────┐   homr（独立 Python 进程，AGPL 隔离）   ┌────────────┐
│ 用户 PDF   │ ────────────────────────► │ 每页 PNG │ ─────────────────────────────────► │ MusicXML   │
│  / 图片    │   （图片谱跳过此步）        │          │   uvx homr page1.png（逐页）         │ （每页一份）│
└────────────┘                          └──────────┘                                      └─────┬──────┘
                                                                                               │ relieur 多页合并
                                                                                               ▼
┌────────────┐  人工校对（必须）          ┌────────────┐   music21 脚本导出小节时间表       ┌────────────┐
│ Song Pack  │ ◄─────────────────────── │ MuseScore  │ ◄───────────────────────────── │ MusicXML   │
│ manifest   │  打开 MusicXML 逐谱修正    │  校对修正   │                                │ （已校对）  │
└────────────┘                          └────────────┘                                └────────────┘
                                                                                               │
                                                                                               ▼
                                            应用运行时：OSMD 加载 MusicXML + 光标跟随 + 主题染色（见 §4）
```

**步骤与命令**：

```bash
# ① PDF → 页面图片（poppler 的 pdftoppm；Windows 可装 poppler 或用 pdf2image）
pdftoppm -png -r 300 乐谱.pdf page
#    r=300 是关键——homr 对低分辨率敏感；图片谱直接使用原图

# ② homr 识别（单页单次；uvx 免安装，或 poetry 安装）
uvx homr page-1.png            # 输出 page-1.musicxml 于同目录
#    多页合并：https://github.com/papoteur-mga/relieur
#    试跑：官方在线 demo https://homr.site 先验证样本谱效果

# ③ 人工校对（不可省略）：MuseScore Studio 打开 MusicXML
#    重点核对：拍号/调号、时值（八分/十六分最易错）、临时升降号、连音线

# ④ 入库：music21 从校对后的 MusicXML 生成小节时间表（Song Pack 所需）
python -c "
import music21
s = music21.converter.parse('乐谱.musicxml')
# 遍历 Measure 的 offset → 输出 [{measure, time}]（按拍号/速度换算秒）
# （MVP 已有此脚本计划，见技术选型 B 节）
"

# ⑤ 应用侧：现有 OSMDScore 加载 MusicXML，accent 传主题金 #d9a441 即可
```

**Windows 注意**：homr 依赖 Python 3.11 + Poetry/uv；CPU 可跑（单页约 15s），有 NVIDIA GPU（CUDA 12.1）更快。建议转换机/CI 脚本化，不塞进浏览器。

### 2.2 变体：Audiveris / Clarity-OMR

- 想**直接吃 PDF**、偏好图形化人工修正 → **Audiveris**：`audiveris -batch -export 乐谱.pdf`，GUI 可逐符号纠错，输出 MusicXML。
- 想要**一行命令 PDF 直出**、有 PyTorch 环境 → **Clarity-OMR**：`python omr.py score.pdf -o out.musicxml`（模型自动下载）。
- 三者（homr/Audiveris/Clarity-OMR）精度同档，选型主要看部署习惯与许可偏好；homr 生态最活跃（Andromr 安卓 App、homr.site 演示均围绕它）。

### 2.3 PDF「直转」可行性澄清（调研方向 3）

- **乐谱软件导出的 PDF 没有语义**：MuseScore/Finale/Sibelius 导出的 PDF 是矢量图形，不内嵌 MusicXML/MIDI 数据，任何解析器（music21、PDF 文本提取）都无法还原音符——**能拿到源文件（.mscz/.mxl）就直接转，拿不到就 OMR**。
- 有源文件时的官方路径：`mscore -o 输出.musicxml 输入.mscz`（MuseScore 4 命令行）；music21 也封装了该转换（`converter` 调 MuseScore）。
- MuseScore 4 已**移除 PDF 导入**功能（2.x 的实验功能），别走这条路。

## 3. 风险与兜底方案

| 风险 | 等级 | 应对 |
|---|---|---|
| **OMR 精度非 100%**：干净印刷谱 ~70–90%，手写/低清/密集和弦显著下降（时值错、调号错、谱线错） | 高 | ① 流程强制人工校对（MuseScore）；② UI 上对「自动识别谱」打标提示可能不准；③ 校验：music21 检查每小节时值总和是否等于拍号（可自动抓一类错） |
| **AGPL/GPL 传染性**（homr/Audiveris/Clarity-OMR） | 高 | 识别进程与 Syrinx 前端**完全隔离**：转换作为独立 CLI/服务（如本地 FastAPI 或 CI 脚本），前端只消费 MusicXML 结果。若未来要提供 SaaS 转谱服务，同进程部署仍合规，但**不得把引擎代码并入闭源前端分发**；oemer（MIT）是无传染风险的第二选择 |
| **多页谱**：homr 单图单 MusicXML | 中 | 逐页识别后用 relieur 合并；或提示用户分页上传 |
| **简谱无成熟 OMR** | 中 | 走录入路线（MuseScore 简谱插件 / domisol / jianpu-ly 文本），输出统一为 MusicXML；P2 再评估自研 |
| **手写谱** | 中 | 无开源可用；PhotoScore 商业版支持手写（仍需核对）；或直接人工录入 |
| **homr 输出缺力度/连音/装饰音** | 低 | 校对阶段在 MuseScore 补；对长笛单旋律曲目影响小 |
| **识别出的 MusicXML 在 OSMD 渲染异常**（罕见布局/元素） | 低 | 技术选型已有 fallback：alphaTab 渲染；或校对阶段顺手简化谱面 |

**兜底方案分级**：
1. **兜底 A（人力）**：用户谱子量小 → 直接 MuseScore/Flat 人工录入，最稳，一条谱 10–30 分钟。
2. **兜底 B（半自动）**：homr/Audiveris 识别 + MuseScore 校对（推荐默认流程）。
3. **兜底 C（自研最小识别器）**：音符/休止符/拍号/调号/连线的图像识别 → 生成 MusicXML。**工作量 20–40 人日**（含数据集标注），精度仍难追 homr——**除非有商业/合规硬约束，不建议**。

## 4. 氛围效果联动：OSMD 染色 API 与主题 A 落地

已对照本仓库安装的 `opensheetmusicdisplay@2.1.2` 类型定义核实（app/src/score/OSMDScore.ts 已用到其中部分）：

| 需求 | OSMD API | 主题 A 落地方式 |
|---|---|---|
| 光标/强调色（暖金 #d9a441） | 构造参数 `cursorsOptions: [{ type, color, alpha, follow }]`，type 1=细竖线 ThinLeft、2=整列高亮、3=底线 | 已实现：`{ type: 1, color: accent, alpha: 0.9 }`，accent 传 `#d9a441`；可加一条 `type: 2` 的低透明度整列高亮增强当前音符 |
| 全谱基础色（数据色晨光青 #5fb8a8 / 暖白音符） | 构造参数 `defaultColorMusic` / `defaultColorNotehead` / `defaultColorRest` / `defaultColorLabel` | 音符头用暖白（`#fdfdf8` 或微调 `#f5ead1` 暖调），休止符/标签用低饱和晨光青系，符合 A 方案配色 |
| 逐音符/逐小节染色（如当前小节强调） | `setColoringMode(ColoringModes.XML | AutoColoring | CustomColorSet)` + `EngravingRules` 色集；XML 模式读 MusicXML `<color>` | 校对脚本批量注入 `<note color="#5fb8a8">` 高亮段落；实现时先验证该 OSMD 版本对 `<color>` 的解析（旧版支持有限），备选方案：SVG 输出后按 CSS 类/滤镜叠加染色 |
| 玻璃面板可读性 | 构造参数无背景色时透明（默认），配合外层容器 | 谱面容器透明 + 玻璃面板背景（backdrop-filter blur）——技术选型 E 已定「暗化/模糊遮罩保证谱面可读」，音符亮色（暖白/金）与晨光青底色错开即可；`EngravingRules.PageBackgroundColor` 可设透明 |
| 暗色模式切换 | `OSMDOptions` 注释：dark mode 即设 defaultColorMusic + PageBackgroundColor | 与主题 A 的玻璃面板天然兼容 |

**结论**：主题 A 所需染色全部落在 OSMD 现有 API 内，且光标金、音符暖白已在当前代码落地；剩余工作量集中在「当前小节/段落强调色」的两种实现路径（MusicXML color 注入 vs SVG 覆盖层）二选一的验证与微调（约 1 人日）。

## 5. 工作量估算

| 项 | 内容 | 估算 |
|---|---|---|
| 转换工具链落地 | homr 安装/脚本化（或 Audiveris）、PDF 转图、多页合并、校验脚本（小节时值检查）、使用文档 | 2–3 人日 |
| 主题染色收尾 | 当前音符/小节强调（color 注入或 SVG 覆盖）、玻璃面板可读性微调 | 1–2 人日（光标金已实现） |
| 人工校对 SOP | 校对指引 + MuseScore 修正清单 + 校验规则（自动化抓时值错） | 1 人日 |
| 简谱支持 | MuseScore 简谱插件录入→导出 MusicXML 的 SOP 与示例曲目 | 0.5–1 人日 |
| 转换服务化（可选 P2） | 本地/自托管 FastAPI 转谱接口（隔离 AGPL 进程），供应用内上传 | 3–5 人日 |
