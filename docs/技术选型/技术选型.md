# 长笛演奏辅助应用 · 技术选型报告

> 对应《需求文档.md》。四个核心模块逐一对比并给出推荐 + 备选，附决策理由与风险。

## 总体架构（Web 单页应用）

```
┌────────────────────────────────────────────────┐
│  前端 SPA（Vite + TypeScript，框架可用 React）     │
│                                                │
│  页面层   曲库首页 │ 预览页 │ 演奏页 │ 回放页      │
│  ──────────────────────────────────────────    │
│  曲谱引擎  OSMD（渲染+光标）     ← 选型 A         │
│  同步引擎  Audio Clock（Web Audio 时间轴调度）    │
│  音频层   伴奏播放 / MediaRecorder 录音          │
│  背景层   <video>/着色器播放器 + 合成叠加         │
│  数据层   Song Pack manifest + localStorage     │
└────────────────────────────────────────────────┘
```

**关键架构决策：以伴奏音频的 Web Audio 时钟为唯一主时钟。**
曲谱光标、自动滚动、节拍提示、背景动画全部从 `audioContext.currentTime` 推导，
不用 `setTimeout`/`requestAnimationFrame` 计时充当时间基准（只能用它做渲染回调）。
这是 OSMD 官方 demo 与多个音频同步实践（ADC 演讲、web.dev）一致的做法。

## A. 曲谱引擎：渲染 + 光标跟随

| 候选 | 输入格式 | 光标/跟随 | 内置播放合成 | 体积 | 维护 | 备注 |
|---|---|---|---|---|---|---|
| **OpenSheetMusicDisplay (OSMD)** | MusicXML | ✅ 内置 Cursor + `FollowError` 自动滚动，可按时间戳定位 iterator | ❌（自配） | ~1MB | 活跃（Pharmaziegasse 团队） | 本项目首选，见下 |
| alphaTab | MusicXML / Guitar Pro / alphaTex | ✅ 内置 synth + 播放高亮 | ✅ Midi+SoundFont 合成器 | 较大 | 活跃（CoderLine） | 功能最全但"吉他向"，MusicXML 渲染保真度略逊 |
| VexFlow | 无（底层绘图库） | ❌ 全部自建 | ❌ | 小 | 活跃 | 是 OSMD 的底层，直接用需自研解析+布局，成本过高 |
| abcjs | ABC 记谱 | ✅ 播放高亮 | ✅（合成简单） | 小 | 活跃 | 需先把 MusicXML 转 ABC，转换有损；适合小作品 |

### 推荐：OpenSheetMusicDisplay（OSMD）

理由：
1. **MusicXML 是曲谱事实标准**，MuseScore/Finale/Sibelius 都能导出，用户自制曲谱路径通畅
2. **光标与自动滚动开箱即用**：`osmd.cursor.show()/next()`，`osmd.FollowError = true`（官方 demo 的 "FollowError" 选项）即自动把光标滚入视口；可通过 `MusicPartManagerIterator` 按 `Fraction` 时间戳精确跳转——这是"按伴奏时钟驱动光标"的关键钩子
3. 演奏提示高亮（当前小节染色）可通过其 EngravingRules / SVG 覆盖层实现
4. MIT 许可，纯浏览器端，TS 类型完备

**代价**：伴奏音频合成需自建（本项目伴奏本来就是外部音频文件，OSMD 不管音频反而干净）。

**备选**：若后期要"应用内合成试听"（P2 试听小样），可叠加 alphaTab 或 Web Audio SoundFont 播放器；若某曲谱 MusicXML 在 OSMD 渲染有问题，alphaTab 是 fallback。

风险：OSMD 光标最小推进单位是"音符位置"，浮动音符的精确亚拍定位要自己插值（用 iterator timestamp + 音符时值做线性插值移动光标层）。

## B. 音频同步：伴奏 + 曲谱时间轴

| 候选 | 精度 | 复杂度 | 说明 |
|---|---|---|---|
| **Web Audio API `AudioBufferSourceNode` + `audioContext.currentTime` 主时钟** | ~ms 级 | 中 | 解码伴奏为 AudioBuffer，记录 `startCtxTime`，任意时刻 `t = ctx.currentTime - startCtxTime` 即曲目时间；所有视觉元素由 rAF 读取 t 更新 |
| HTML5 `<audio>` + `audio.currentTime` | 50–200ms 抖动 | 低 | 简单但 currentTime 粒度粗、更新节流不可控，光标会抖 |
| Web Audio + 分析 波形对齐/DP | 高 | 高 | 无必要 |

### 推荐：Web Audio 时钟方案

- 伴奏解码为 `AudioBuffer`，经 `GainNode`（音量）→ `destination`
- **时间轴元数据**：Song Pack 里附带由 MusicXML 导出的小节时间表（`[{measure:1, time:0.0}, {measure:2, time:2.4}, ...]`，构建期从 MusicXML 的拍号/速度或从 DAW 导出对齐点生成）——光标推进直接查表，避免运行时猜测
- 用户变速（P1-2）：`AudioBufferSourceNode.playbackRate` 全局生效，时间轴按同一 rate 换算，谱/音天然保持同步
- 蓝牙耳机 `outputLatency` 不可忽视：提供"音频延迟校准"设置（播放节拍音让用户点按，测偏移量），练琴推荐扬声器

**风险**：伴奏与曲谱由不同来源制作时对不齐 → 靠小节时间表 + 手动偏移字段（manifest 里 `offsetMs`）兜底。

## C. 音高检测（P2，MVP 不做，但选型先行）

| 候选 | 方式 | 精度(长笛场景) | 浏览器可行性 | 备注 |
|---|---|---|---|---|
| **CREPE (tf.js / WASM)** | 深度学习 | 高（低信噪比也好） | 模型 ~MB 级，需 WebAssembly/tfjs 后端，移动端吃力 | 调研到的主流方案 |
| **MPM / YIN (WASM, 如 microdsp)** | 信号处理 | 中（安静环境足够） | Rust→WASM，轻量流畅 | 长笛音色纯净，单音检测 MPM 足够 |
| autocorrelation (纯 JS) | 信号处理 | 低-中 | 无依赖 | 原型可用，八度误判多 |

### 推荐：MVP 阶段不接音高检测；P2 先做 **MPM/YIN(WASM)**，不够再上 CREPE

理由：长笛是单音乐器、音色谐波干净，MPM 在安静室内已可达可用精度，且零模型体积、零 GPU 压力；CREPE 精度上限更高但移动端性能与加载成本大，留作增强。Pinia 参考：PitchPlease、microdsp web demo 均为此路线。

风险：浏览器 `getUserMedia` 需 https 或 localhost；长笛高频泛音要在 `AnalyserNode` 上用 ≥44.1kHz 采样、1024+ FFT 窗长。

## D. 录音与回放

| 候选 | 说明 |
|---|---|
| **MediaRecorder API** | 原生、简单、输出 webm/ogg；保存 blob 直接 `<audio>` 回放 + 下载 |
| Web Audio `ScriptProcessor/AudioWorklet` 采集 PCM + WAV 编码 | 兼容性最稳、可后处理（降噪/裁剪），工作量较大 |
| 两者结合（推荐路线） | MVP：MediaRecorder 直接出 webm；P1 若需裁剪/格式转换，切到 AudioWorklet 采集 |

### 推荐：MediaRecorder（MVP）

要点：
- `getUserMedia({audio: {echoCancellation:false, noiseSuppression:false, autoGainControl:false}})`——演奏录音要**原始音色**，关闭浏览器默认处理，避免长笛高频被降噪吃掉
- 演奏页同时播放伴奏 + 录音：**只录麦克风**，不混伴奏（回放页可"伴奏+录音"双轨对齐播放，因为两者共用同一时间轴）——用户想导出混合音频是 P1 的混音功能
- iOS Safari 的 MediaRecorder 支持已可用（webm 不支持时 fallback mp4），但 iOS 整体仍为 P1 适配目标

## E. 动态背景

| 候选 | 说明 | 定位 |
|---|---|---|
| **预渲染视频（mp4/webm, loop）** | 用户外部生成（AE/Blender/AI 视频工具），`<video muted loop>` 叠在底层，播放器只控制透明度/滤镜 | **MVP 主方案**：零运行时开销、效果上限高、可离线 |
| three.js audio-reactive 着色器 | 运行时由伴奏 FFT 驱动；调研到多个开源实现（audio-reactive-shaders、phase-viz、Shader Park 教程）可借鉴 | P2：做"内置生成器"时再引入，作为无素材曲目的 fallback |
| CSS/canvas 粒子 | 简单但廉价感风险高 | 仅作加载态 |

### 推荐：视频底 + 合成叠加

叠加栈（自下而上）：`动态背景视频 → 暗化/模糊遮罩（保证谱面可读，硬约束）→ 曲谱层(OSMD SVG) → 光标/节拍高亮 → 控件层(自动隐藏)`。
视频以曲目 manifest 指定，缺省 fallback 到全局默认背景；`prefers-reduced-motion` 时自动暂停视频只用静态封面。

## F. 工程栈建议

| 层 | 选择 | 理由 |
|---|---|---|
| 构建 | Vite + TypeScript | OSMD/alphaTab 均有 TS 类型；HMR 快 |
| 框架 | React（或 Vue，均可） | 页面少、状态简单（当前曲目/时间轴/录音状态），框架只为组件化与路由 |
| 状态 | zustand（或组合式 store） | 时间轴用 rAF 直接驱动 DOM/SVG 更新，**不进响应式状态**（每帧 setState 会卡） |
| 路由 | react-router / vue-router | 4 个页面足够 |
| 样式 | 原生 CSS + CSS 变量（暗色主题） | 参考技能库 popular-web-designs 的 Spotify/Netflix 风格 token |
| 部署 | 静态托管（本地起服务 / 云服务器静态目录） | 无后端也能跑；将来加账号/存储再补服务端 |
| 测试 | Vitest（时间轴工具函数）+ 手动演奏测试 | 时间轴换算是唯一强单元测试点 |

## 决策汇总

| 模块 | 推荐 | 备选/升级路径 |
|---|---|---|
| 曲谱引擎 | **OSMD** | alphaTab（渲染问题时）、VexFlow（自研底座，不建议） |
| 音频同步 | **Web Audio 时钟 + 小节时间表** | HTML5 audio（快速原型） |
| 音高检测 | **P2：MPM/YIN(WASM) 先行** | CREPE/tfjs（高精度需求） |
| 录音 | **MediaRecorder** | AudioWorklet+PCM（需要后处理时） |
| 动态背景 | **外部视频 + 遮罩叠加** | three.js shader 生成器（P2） |
| 工程栈 | Vite + TS + React + zustand | Vue 等价替换 |
