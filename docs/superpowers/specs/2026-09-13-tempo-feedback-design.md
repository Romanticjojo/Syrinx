# Tempo control and faster performance feedback

User authorization: implement BPM adjustment on dev and web-deploy, keep accompaniment/cursor/recording synchronized, optimize slow pitch feedback, verify responsive UI with the built-in browser. This extends the authorized v0.3.0 release and bilingual README work.

- Initial BPM uses the loaded timeline's initial tempo. One session-wide speed ratio preserves written tempo changes. The compact control displays the selected reference BPM, with a small panel containing a numeric field, slider, recommended-value reset and Apply button. Supported ratio: 0.5–1.5. The draft does not affect transport until applied.
- Accompaniment must preserve pitch. Keep the existing Web Audio buffer path at original speed; after a speed change use a local WAV media element with native preservesPitch routed through the same gain/analyser. Use its actual currentTime as the sole song-position source on that path. No external audio service or new runtime dependency. Unsupported pitch preservation must fail clearly without silently transposing.
- Applying speed is a transport transaction: invalidate previous play/count-in requests, pause, seal the old capture, prepare the new rate, retain song position, then re-count if previously playing. Ready/paused states stay stopped. Quick repeated operations must let only the latest intent resume. Count-in scales by the chosen rate. A segment stores a fixed playbackRate; recorded local seconds map to song seconds as startSec + localSec * playbackRate.
- Replay uses the segment rate for accompaniment, and pitch analysis maps measured times to the original timeline before scoring. Original recordings are played at normal speed. Switching segments cannot leak stale playback or stale analysis.
- Optimize the proven pitch-analysis bottleneck while retaining useful long-flute accuracy. Move heavy work off the UI thread where supported, bound computation to the relevant pitch range, report progress, and cancel obsolete work. Retain a responsive fallback. Optimize chart drawing where measurements justify it; do not reduce scoring input merely to simplify rendering.
- Test controls and dialogs at 320/390/540/768/820/1024 px and desktop widths. Touch targets stay at least 44 px. Draft input keyboard events cannot trigger global transport shortcuts. No claims of native hardware validation from viewport emulation.
- Publication: dev v0.3.0 and web-deploy v0.3.0-web; same illustrated Chinese/English documentation, documentation-only update on GitHub default master. No cloud deployment or native installer delivery in this change.
